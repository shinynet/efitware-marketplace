# Releases and compatibility

The application owns its product DTOs, MCP tools, authentication, permissions and database. This repository owns the plugin, coaching instructions, embedded training views, and the card's consumer projection. No source import crosses that boundary.

`apps/workout/lib/PROVENANCE.json` records the source commit/hash and copied-file hash for extracted helpers and theme assets. The hashes document intentional copying. `contract/compat-fixtures.json` independently checks behavior in both repositories: root section order, nested set/activity slots, stable ties, unit thresholds, formatting, and localized input round-trips. Updating a copy requires updating provenance and reviewing the behavioral fixtures.

`pnpm build` bundles Vue, fonts, brand assets and theme tokens into `dist/card/workout.html`, then generates the open draft-07 input schema. The product validates its raw tool output against that schema using Ajv without stripping extra fields, applying defaults or coercing types. The product DTO remains authoritative.

## Workout Library card and tools (0.1.26)

Tool inventory, card, schema and skill change (application EF-1607, epic EF-1536). The application exposes its authored workout Library to external assistants: `search_workout_library`, `get_workout_library_item` and `preview_workout_library_item` (supporting reads), `save_workout_library_workout` (an undoable write that saves a previewed Workout to Saved workouts) and the display tool `open_workout_library`. Programs are read and preview only. There is no Coach substitution: the assistant is the AI in that conversation. The inventory grows to 124 tools (67 reads, 57 writes), and `minimumAppCommit` is the application commit that registers them.

- **Manifest format 8.** The release adds `contract/workout-library-view.schema.json`; formats 1–7 keep their exact inventories for rollback. The application accepts format 8 in the change that pins this release.
- **Schema.** `open_workout_library` returns `{ view: 'workout-library', record, related: {}, presentation }`. `record.mode` is `browse` (the search result: `trainingSpace`, `query`, `data`, `meta`) or `item` (one item with `description`, `suitability`, `trainingSpace`, `content` and `exercises`). Every item carries a `fit`: `needs-space`, `exact`, `adaptable` with `swaps` (`slotId`, optional `exerciseId` and `name`, `cause` and `missingEquipment`) or `unavailable` with a `reason`, `slotIds`, `exercises` and optional `missingEquipment`/`requiredDays`. A Program item (browse or detail) may carry `programWeek` (`weekStart`, `capacity`, optional `variantId`): the week whose remaining capacity its fit was evaluated against. The projection is open like every other view.
- **Card.** Browse shows each item's format, minutes, fit badge and fit sentences, with paging through `open_workout_library`; an item opens inside the same iframe and shows its fit for the named Training Space, each swapped exercise with the equipment the space lacks, who it suits and every session's exercises with their set summary. Opening a Program, refreshing it and returning to the results keep the evaluated week (`weekStart`), so its fit does not change on the way. A Workout never takes a week, because the application refuses one; the application pages have no week parameter, so links leave it out. An unconfigured space says it needs setup and guesses nothing. The card never previews or saves: an exact or adaptable Workout offers one host follow-up ("Ask my AI to prepare this"), and a Program points to the app. Links open `/library` (with `space` when it is not the default, and the facets in force) or `/library/<id>`. English and German. Facet and fit labels are a projection of the application's `i18n/features/workout-library` catalog, recorded in `apps/workout/lib/PROVENANCE.json`.
- **Skill.** A "Workout Library" section: suggest a fitting Library item first when the user doesn't know what to train; preview before offering to save, and explain the fit and every swap honestly; save only on request, then open the saved workout; give the reason for an unavailable item; record equipment for a space that needs setup; Programs read and preview only. `open_library` and `search_exercise_library` are named the exercise catalog. ## Supersets and circuits (0.1.24)

Tool inventory, card, schema and skill change (application EF-1552, TECH-A1). Workouts and templates can carry persisted `executionGroups`: a `superset` (exactly two exercises) or `circuit` (2–10) over the record's own exercise instance and set ids, `{ id, kind, members: [{ workoutExerciseId, setIds }] }`. Round N runs each member's Nth selected set in member order; a member's other sets run before round 1. Rest is not part of a group: it is the ordinary rest Activity after the set it follows.

- **Tool.** `update_execution_groups` replaces the complete list on one workout (`workoutId`) or template (`templateId`) in that instance form; `[]` ungroups. It mirrors the application's `PUT …/execution-groups` resources and is undoable through `undo_action`. `contract/server-contract.json` and `view-coverage.json` carry it (an `action` on the workout and template views, host-mediated); `minimumAppCommit` is the application commit that registers it.
- **Schemas.** `contract/workout-view.schema.json` (`workout.executionGroups`) and `template-view.schema.json` (`record.executionGroups`) admit the optional group list: at most 20 groups, 2–10 members, 1–100 set ids each, kind `superset` | `circuit`. The projections stay open like every other view field; the application enforces the cross-reference rules.
- **Card.** Before a group's first member, the workout and template views show a labelled block: "Superset" or "Circuit", the round count, the member exercises in order, and each round's turns (exercise and set number) with the Activities the record already saves after each selected set, including an explicit 0 s rest, a rest after each round and several blocks in one slot. The members' own rows still render in full below. The card cannot edit a grouping, so its only group action, "Change grouping in eFitware", opens the record's own application page (the same page as the header link). A reference the record does not hold shows no block rather than a partial one. English and German.
- **Skill.** A "Supersets and circuits" section explains the rules, the index form on full-tree writes (`create_workout` explicit trees, `create_template`, `update_template` with `exercises`, each `save_week_plan` entry: `{ kind, members: [{ exerciseIndex, setIndexes }] }`), the instance form in `update_execution_groups`, that rest is an Activity, and that routine edits refuse to break a group. The refusal table adds the four group refusals (`WORKOUT_EXECUTION_GROUPS_INVALID`, `WORKOUT_EXECUTION_GROUPS_REQUIRED`, `WORKOUT_EXECUTION_GROUP_MEMBER_REFERENCED`, `WORKOUT_EXECUTION_GROUP_ORDER`) with their remedies.

`contract/compat-fixtures.json` gains `executionGroups`: grouped `open_workout` and `open_template` payloads as the application emits them. `contract/execution-groups.test.ts` validates them against the published schemas, checks that invalid groups are refused and extra fields preserved, derives the rounds and their saved rests, renders the template card in English and German (and nothing extra for a sequential template), and proves the grouping action is a single link button to the record's application page.

## Personal-record award kinds (0.1.23)

The application awards at most one personal record per exercise per workout, of two kinds: Heaviest (`weight`, a new maximum weight at any reps) and Est. 1RM (`oneRm`, a new best Epley estimate from a set of 1 to 12 reps). The first workout with an exercise sets the reference and earns nothing, and `volume` is no longer awarded.

- **Schemas.** A progress `recentPrs[]` row admits `type` (`weight` | `oneRm`) and `estimatedOneRm`; an exercise-progress `records[]` row admits `estimatedOneRm`. `estimatedOneRm` is the Epley estimate of the lifted set as a whole-unit measurement object in the account's unit (the same shape as every other estimate); `weight` and `reps` stay the lifted set. Both fields are optional, so an application that predates EF-1468 still validates. The stored-marker schema still admits `volume` and `first`: markers written under the old rules persist until the application's refresh (EF-1470), and their removal is EF-1471.
- **Views.** A recent PR reads "Heaviest 187.5 lb · 6 reps" or "Est. 1RM ~215 lb · from 170 lb × 8"; a records row adds the same kind line under its set. The card decides a records row's award from its stored markers exactly as the application's `presentedPrAward` does: Heaviest outranks Est. 1RM, and a `volume` marker, a `oneRm` marker from a set outside 1 to 12 reps, or a `weight` marker without reps presents none. A records row that presents no award is not shown; a page holding only such rows shows the empty state, and paging still follows the application's page. The application also filters these rows before paging, so this is a safety net for deployments that predate that fix. A recent PR without `type` renders as before, without a kind. German reads "Höchstgewicht" and "Gesch. 1RM … · aus …", matching the application.
- **Copy.** The count reads "Personal record awards", and the recent-PR note reads "Latest six in this window. Each is one award: at most one per exercise per workout." The retired "Set volume record" label is gone.
- **Skill.** The grounding rule on personal records adds that a PR is an award, at most one per exercise per workout, Heaviest or Est. 1RM (stated as an estimate with its source set); that the first workout with an exercise earns none; and that a stored `volume` marker, or a `oneRm` marker from a set over 12 reps, is not an award and is never announced. `contract/plugin.test.ts` pins the rule.

## Measurements carry their unit (0.1.22)

Card, schema and skill change (EF-1447, app plan "Imperial accounts" §1 and §6). The cards and skill adopt the MCP measurement contract: every weight and body measurement an assistant or card reads is a measurement object `{ value, unit }` already in the account's unit, and the card renders it as given. The `weightUnit: 'kg'` metadata is gone; `presentation.unitSystem` stays only as a hint for the unit of a value typed into an empty field. The card never converts a measurement a second time: `{ value: 85, unit: 'kg' }` on an imperial payload reads "85 kg".

- **Loads** (a set's `weight` and `plannedWeight`, set PR markers, `stats.topSet.weight`, progression `bestSetWeight`, personal-record `weight`, recent-PR `weight`) are `{ value, unit: 'lb' | 'kg' }` on the unit's grid, half a pound or 0.25 kg (`multipleOf` in the schemas). They render with at most one decimal for lb and two for kg ("187.5 lb", "85.25 kg"). The card sends an edited set weight as a measurement object in the unit it showed.
- **Totals and estimates** (the `volume` headline metric, `weeklyVolume[].volume`, estimated one-rep-maximum series points) use the same shape with whole-number values, rendered whole. The workout card sums its completed volume only when the loads share a unit.
- **Body metrics** use unit-free identifiers `weight`, `neck`, `shoulders`, `chest`, `waist`, `hips`, `biceps`, `forearms`, `thighs`, `calves`, `body_fat` and `resting_heart_rate`, with units `kg|lb`, `cm|in`, `percent` and `bpm` respectively (bpm is a whole number). They render unsnapped at one decimal; bpm is whole. The progress body section reads `weight`, `goalWeight` and `bodyFat`, and its measurements, like the training context's profile (`weight`, `goalWeight`, `bodyFat`, `restingHeartRate`, `measurements` keyed by identifier), carry measurement objects; `heightCm` is unchanged. A dated point or observation is `{ date, value: { value, unit } }`, and `open_body_metric` takes the identifier as `key`.
- **No twin fields.** The schemas refuse bare-number loads, totals and body values, off-grid loads, fractional totals, wrong-dimension units and the suffixed body-metric keys (`weight_kg`, `waist_cm`, …). The suffixed field names (`weightKg`, `volumeKg`, `valueCm`, `bodyFatPercent`, …) are replaced by the unit-free names above, not accepted beside them.

`contract/compat-fixtures.json` gains `measurementContract`: `open_workout` payloads with imperial (187.5 lb) and metric (85.25 kg) loads, an `open_exercise_progress` payload (a top set on the grid, whole-unit estimates, history and records), an `open_progress` payload (whole-unit volume, loads, body and cardio measurements), one `open_body_metric` payload per identifier in an imperial account plus metric `weight` and `waist`, and an `open_context` payload. `contract/measurement.test.ts` validates each against the published schemas. The skill states the contract: read and send measurement objects, never convert, send the unit the user said, and use the unit-free body-metric identifiers. The regenerated schemas are `workout`, `template`, `progress`, `exercise-progress`, `body-metric` and `context`. No tool inventory change, so `minimumAppCommit` is unchanged.

This release builds on 0.1.21 and includes its calendar contract (0.1.20). The application pins it in EF-1448, the change that starts emitting these shapes, and that change must follow EF-1477. The current application's kilogram payloads fail these schemas, so this is a staged prerelease. Catalog promotion and `channels.json` follow only after that application deployment is READY in production.

## Missed and ended calendar days (0.1.20)

Card and schema change (EF-1474, app plan "Done, missed and planned scheduled days"). The calendar view admits the application's new presentation contract. A day's `status` is `in_progress`, `missed`, `planned`, `completed`, `ended` or null, in that precedence: the highest bucket present, so a `completed` day is not a claim that every session was completed. `incomplete` is renamed `planned`, with no alias. Each day also carries `inProgressSessionCount`, `plannedSessionCount`, `missedSessionCount` and `endedSessionCount` beside `sessionCount` and `completedSessionCount`, and `sessionCount` is their sum. Every agenda row carries `displayStatus` (a workout status or `missed`); `status` stays the lifecycle value, and occurrence rows stay `planned`. `missed` and `ended` are presentation only: the canonical workout schema (`apps/workout/model.ts`) is unchanged.

Each day shows one mark per session, in the order completed, in progress, planned, missed, ended. Shapes differ without colour, and every mark has an accessible label: a filled dot for done, a ring for planned, a muted ring with a diagonal slash for missed, a muted ring with a short bar for ended (skipped or abandoned), and a ring with its left half filled for in progress (terracotta). No two marks differ by colour alone. Missed agenda rows read "Missed" and offer "Log past workout", which records on the original date: a missed occurrence is saved on its date, and a missed saved workout opens. Skipped and abandoned rows keep their terminal labels. The compact card's agenda line uses `displayStatus`. `contract/calendar-view.schema.json` is regenerated, and `contract/compat-fixtures.json` gains `getCalendarResponse`, one representative `get_calendar` response covering a day trained by hand, a missed day, a planned day, a mixed past day (done plus missed), a skipped-only day and an abandoned-only day. No tool inventory change, so `minimumAppCommit` is unchanged. ## Stage

1. Prepare a reviewed release branch. Bump both plugin manifest versions together. Keep `main` on its published catalog version while staging.
2. Build and verify with `pnpm build`, `pnpm typecheck`, `pnpm lint`, and `pnpm test`. Confirm two card builds have identical SHA-256 values.
3. Push an annotated `v<version>` tag at the reviewed release commit. The stage workflow checks tag/version agreement and publishes the complete asset set as a prerelease. GitHub locks the tag and assets at publication. Fix mistakes in a new version.
4. Record the manifest SHA-256. Its file entries contain logical paths, exact byte counts/hashes and GitHub asset filenames. GitHub assets have flat names: `contract/workout-view.schema.json` is downloaded as `workout-view.schema.json`, then installed at its logical path.

The local equivalent is `pnpm release:build --output <new-directory> --strict` after building from a clean commit. It refuses an existing destination. ZIP entry timestamps and ordering are fixed for reproducibility. The explicit packaging allowlist never includes repository history or environment files.

## Verify and promote

1. Pin the staged tag and manifest hash in `efitware-app`'s `efitware-marketplace.lock.json`.
2. Run the application's contract fixtures and real tool/resource checks for both SDK generations. Verify the deployed application provides every tool in `serverContract`, and its production deployment reaches READY.
3. Merge the release branch into `main` using a merge commit or fast-forward. Never squash or rebase: the tagged commit must remain an ancestor of `main`. Update both catalogs, both plugin manifests and `channels.json` together, setting `published` to the verified version and `staged` to null.
4. Clear the GitHub prerelease flag. Download the manifest again and compare its SHA-256 with the staged value. No release asset changes during promotion.
5. Advance the website's pinned static mirror only after compatible application deployment. Verify plain HTTP cloning and existing-client upgrade through the same marketplace URL.

## Roll back

Restore the application's previous lock file and deploy it. Add a new `main` commit restoring the previous catalog/plugin versions and channel; never rewrite published Git history. Repoint the website mirror pin atomically with its metadata. Previous immutable artifacts remain available. For the initial extraction, the pre-extraction app commit and its unchanged 0.1.1–0.1.6 downloads remain the rollback baseline.

Automated bridge tests do not establish Desktop rendering or authentication continuity. Record fresh installation, existing-install upgrade, rollback, and preserved authentication in actual clients, including the separate Windows-local and Mac-remote host cases.
